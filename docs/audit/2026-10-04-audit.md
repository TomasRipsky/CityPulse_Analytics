# CityPulse audit — 2026-10-04

A full review of CityPulse seven months after it was built (6–10 March 2026), before deciding
how to close it. Everything below was checked against the code, the warehouse and the sources;
nothing is inferred from the README.

## Verdict

The architecture is sound and the intent behind it is good — a medallion lake, keyless CI,
idempotent loads, dbt with tests, a free-tier budget. **The numbers it produced are not.** Only
**40% of the Citi Bike trips** it claims to analyse ever reached BigQuery, every timestamp is
local time labelled as UTC, the "correlation" metrics are ratios that explode near 0 °C, and
the five months of data are all winter months, so the project's question cannot be answered
from what it holds. CI tested the production tables, not the pull request, which is why none of
this was caught. The pipeline stopped on 3 June 2026 and the GCP project's billing is now off.

## Findings

### Critical

#### C1 — Only 40% of the Citi Bike trips were loaded

Each monthly ZIP holds **several CSV files** — 2 to 4 in the months loaded, a new file every
million rows.
`CitibikeProcessor.process_month` opens the first `.csv` in the archive and ignores the rest:

```python
csv_filename = [f for f in zf.namelist() if f.endswith(".csv")][0]
```

The archive order is not the name order, so the file read is arbitrary. Evidence: four of the
five months hold exactly 1,000,000 or fewer rows, and November 2025 starts on the 14th because
the file read was `_4`, the remainder file.

| Month | Files in ZIP | File read | Rows loaded | Trips published (est.) | Share |
|---|---|---|---|---|---|
| Jan 2025 | 3 | `_1` | 1,000,000 | ~2.12 M | 47% |
| Nov 2025 | 4 | `_4` | 417,052 | ~3.41 M | 12% |
| Dec 2025 | 3 | `_2` | 1,000,000 | ~2.09 M | 48% |
| Jan 2026 | 2 | `_2` | 816,391 | ~1.82 M | 45% |
| Feb 2026 | 2 | `_1` | 1,000,000 | ~1.22 M | 82% |
| **Total** | | | **4.23 M** | **~10.66 M** | **40%** |

*Estimate: uncompressed bytes of all files × rows per byte of the file that was loaded.*

**Impact.** Every mobility number — `total_rides`, `rides_per_day`, member and electric shares,
station counts — is wrong, by a different factor each month, so even trends between months are
meaningless. `assert_mobility_rides_sum` and the `unique` tests pass because the data is
internally consistent; no test compares what was loaded with what the source published.

**Fix.** Read every CSV member. Add a reconciliation check: rows in Silver = rows across the
month's CSVs, and a dbt test that every day of a loaded month has trips.

#### C2 — The design cannot answer "how does weather affect ridership?"

- **Grain.** The only model that joins the sources, `monthly_city_pulse`, has one row per month:
  **five rows**, all winter (four "Freezing", one "Cold"). No method finds a weather effect in
  five points that barely vary. Daily data — weather and trips per day — gives hundreds of points
  and the variation (rain vs dry days, weekdays vs weekends) the question needs.
- **Metrics.** `casual_rides_per_degree = rides_casual / temp_avg_c` divides by a Celsius
  temperature near zero: **−331,730** in December 2025 (mean −0.33 °C). `rides_per_mm_rain` has
  the same flaw. Ratios to an interval scale are not correlations.
- **Coverage.** Trips exist only for Nov–Feb (plus January 2025), so there are no warm months
  to compare against.

**Fix.** A daily mart (one row per day: trips, members/casual, weather, AQI, weekday,
holiday) over at least twelve months; measure the relationship with `corr()` or a simple
regression, controlling for weekday and season; drop the ratio metrics.

### High

#### H1 — Timestamps are local time labelled as UTC

The extractors ask Open-Meteo for `timezone=America/New_York`, which returns local wall-clock
times without an offset; the processors then parse them with `utc=True`. Citi Bike CSV times are
local too and get the same treatment. Evidence: weather for 2026-01-15 runs from 00:00 to 23:00
"UTC" (NYC midnight is 05:00 UTC in January), and the busiest trip hour is 17:00 "UTC" — the
local evening rush.

Daily aggregates are right by accident, because every source is wrong the same way. Any hourly
analysis, any join with a correctly-timed source, and every timestamp shown in a dashboard is
off by four or five hours. **Fix:** localise to `America/New_York`, then convert to UTC (or ask
Open-Meteo for `timezone=GMT`), and keep a local `date` column for daily grains.

#### H2 — CI tests production, not the pull request

The dbt job runs `dbt compile` and `dbt test` with a profile pointing at the production datasets
(`generate_schema_name` ignores the target). Models changed in the PR are compiled but never
built, so the tests run against tables built from `main`. A PR that breaks a model passes CI;
a PR that fixes one can fail. It only runs for PRs that touch `transformation/`, and never on
the Python. **Fix:** `dbt build` into a PR-scoped dataset (and drop it afterwards), plus lint and
unit tests for the Python on every PR.

#### H3 — Loads are not atomic, errors are swallowed, and the documented partitioning does not exist

- Loaders run `DELETE … where date = …` and catch **every** exception as "no existing rows". A
  delete that fails for any reason (permissions, quota, streaming buffer) is followed by an
  append that duplicates the day.
- The README promises day-partitioned weather/air tables and month-range-partitioned trips with
  clustering. `LoadJobConfig` sets neither; `bq ls` shows no partitioning or clustering on any
  table. Each delete scans the full table.
- SQL is built with f-strings instead of query parameters.

**Fix:** create the tables partitioned (Terraform or the first load) and load with
`WRITE_TRUNCATE` into the partition decorator (`weather$20260115`): one atomic statement, no
delete. Let errors raise.

#### H4 — One service account can make itself project owner

The same `citypulse-sa` is used by the VM, by CI on every branch, and by Terraform. Beyond its
Terraform-managed roles, the setup grants it by hand `roles/resourcemanager.projectIamAdmin`
(it can grant itself any role, including Owner), `roles/compute.admin`, `storage.admin` and
`serviceAccountUser` on itself. The WIF condition only checks the repository, so any workflow
on any branch can assume it. **Fix:** separate identities — a CI account with BigQuery access to a
CI dataset only, a deploy account usable only from `main` (`attribute.ref`), the runtime account
with data roles only — and every binding in Terraform.

#### H5 — Code is deployed by `git pull` inside the tasks

`extract_*` tasks run `git pull` on the VM before importing the code, and DAG files are copied
by hand. Two tasks of the same run can execute different versions; a broken commit on `main`
breaks the next run with no review gate; a failed pull fails ingestion. `Variable.get` at module
level queries the metadata database every time the scheduler parses the file. **Fix:** deploy a
versioned artefact (an image or a pinned package) on merge; read Variables through templates.

#### H6 — The stack is past end of life

| Component | In use | Status on 2026-10-04 |
|---|---|---|
| Apache Airflow | 2.8.1 | 2.x end of life since 2026-04-22; current 3.3.x |
| dbt-core / dbt-bigquery | 1.7.0 | End of life; removed from the dbt platform 2027-01-31; current 1.12 / 2.0 |
| Python | 3.11 | Supported, but below the lab baseline (3.12+) |
| Terraform | 1.5.0 pinned in CI, provider `google ~> 5.0` | Current: Terraform 1.16, provider 8.5 — three majors behind |

#### H7 — Nothing alerts, nothing checks freshness

`email_on_failure` is off and there is no other channel. March 2026 trips were due on 8 May and
never reached Silver, while the daily DAG kept running on the same VM; the gap went unnoticed.
There are no source-freshness checks and no row-count expectations. The DAGs run `dbt run` but
never `dbt test`, so bad data reaches the marts and the dashboard. **Fix:** `dbt build` in the
DAGs, `dbt source freshness`, failure notifications, and the lab's Grafana for run health.

### Medium

- **M1 — No tests, lint or lockfile for the Python.** Three `requirements.txt` with
  conflicting pins installed into one virtualenv (`google-cloud-bigquery` 3.17.2 for the loaders,
  3.13.0 for dbt). No `pyproject.toml`, `ruff`, `pytest` or `uv`.
- **M2 — The lake path convention is written six times** (Bronze loader, base processor, Silver
  loader, three BigQuery loaders) plus nine near-identical runner CLIs and six near-identical DAG
  callables. One module for paths and one CLI remove most of it.
- **M3 — A month of trips is processed in pandas on a 1 GB VM.** The ZIP (400–670 MB) and every
  row are held in memory; the docstring claims chunked processing that the code does not do.
  Loading all files (C1) would make it two to four times worse. BigQuery can load the CSVs
  directly from GCS, or DuckDB/Polars can stream them.
- **M4 — Terraform hygiene.** State lives in the data-lake bucket it manages; a personal IP is
  the committed default of `my_ip`; `terraform apply -auto-approve` runs on every push to `main`
  with no environment approval; no budget alert; no tested destroy path (`force_destroy = false`
  and the state inside the bucket). Files named `maint.tf` and `Iam.tf`.
- **M5 — dbt details.** Sources hardcode the project id; `tests:` is the deprecated key
  (`data_tests:` since 1.8); mart tables end in `order by` (BigQuery does not keep it — cost for
  nothing); `pct_hours_good_air` leaves `Hazardous` hours out of its denominator.
- **M6 — `backfill.py` is hardcoded.** Months and skip dates are literals in the file
  (`(2025, 1)  # Noviembre 2025`), it covers weather and air quality only, and it duplicates the
  DAG logic.
- **M7 — A silent filter in `stg_citibike`.** It keeps only trips whose start month equals the
  file's month, to stop trips that start on the last evening of a month and appear in the next
  month's file from creating duplicate days (207 trips in January 2025). Whether those trips
  also appear in the previous month's file was not checked; if not, they are lost. Either way the
  rule belongs in a test or a documented reconciliation, not a hidden `where`.

### Low

- **L1 — Docs drift.** Two READMEs (Spanish and English) that disagree with the code: partitioning
  (H3), file names (`main.tf`, `sources.yml`, `outputs.tf`), a committed `.env` in the tree, `cd
  citypulse-analytics` for a repo named `citypulse_analytics`, a dashboard marked done without a link.
- **L2 — Repository hygiene.** `logs/dbt.log` (a Windows dev log) is committed; the stale
  branch `feat/add-dag-prefixes` has no commits beyond `main`; repo description is "Data
  Engineering project" with no topics; `main` is unprotected; many commits are titled "test" or
  "Updated".
- **L3 — `admin` / `admin`** is the documented Airflow login. The UI was only reachable through
  an SSH tunnel, but it is a poor example in a public repository.
- **L4 — Unused flexibility.** `BaseProcessor.process(date)` on the trips processor only
  forwards to `process_month`; the abstract `load(**kwargs)` contract has three different
  signatures. Small, but it hides that trips are a different shape of source.

## What was done well — keep it

- **Medallion layout** with raw payloads kept, typed Parquet, Hive-style paths and a 90-day
  Bronze lifecycle ([ADR 0002](../decisions/0002-medallion-lake-in-one-gcs-bucket.md)).
- **No keys anywhere**: Workload Identity Federation for CI ([0005](../decisions/0005-workload-identity-federation-for-ci.md)).
- **Idempotency as a requirement** from day one, even if the implementation needs work ([0004](../decisions/0004-idempotent-delete-then-append-loads.md)).
- **Retries with exponential backoff** (`tenacity`) and `--dry-run` on every runner.
- **Cost discipline**: e2-micro free tier instead of Composer, staging as views ([0003](../decisions/0003-airflow-on-a-free-tier-vm.md)).
- **dbt practice**: layered models, a custom generic test, singular tests, full column docs and
  lineage ([0006](../decisions/0006-dbt-staging-views-and-mart-tables.md)).
- **Thought-through cadence** for a late, monthly source ([0007](../decisions/0007-citibike-monthly-with-two-month-lag.md)).
- **Security basics**: uniform bucket access, firewall limited to one IP, path-filtered CI.
